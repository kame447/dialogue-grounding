# 開発・運用記録と作業資産の整理

## 文書の役割

研究目的・採用済み実験計画・評価方針の正本は [dialogue-model/README.md](../dialogue-model/README.md)、アノテーション設計は [annotation/](../annotation/) にある。この文書は開発と運用の進め方を扱い、研究条件を追加・確定しない。デプロイの手順は [公開版README](../workers/tangram-experiment/README.md)、接続と保存復旧の手順は [runtime README](../dialogue-model/runtime/README.md) を参照する。

実装の変更と採否は [Issue](https://github.com/kame447/dialogue-grounding/issues) と [PR](https://github.com/kame447/dialogue-grounding/pulls) に残す。私的な運用記録の入口は、その作業記録ルートの CURRENT.md に集約する。確認した日時、担当、実際の本番反映、受入で確認できた範囲、残件と次に動く条件を記録し、詳細な証拠へリンクする。過去の STATUS.md や日付付きレビューは履歴として保持し、古い担当表や承認待ちを現在の指示として再適用しない。

私的な記録、未公開の評価資料、実対話、盲検の対応表、資格情報を、運用文書の整備を理由にGitやCIログへ移さない。

## 予備実験への影響と優先度

予備実験の開始・完走・復元・提出を妨げる問題、対象や命名合意の重大な誤り、記録・採点・割付・比較条件・プライバシーの破綻を、開始前に解消するP0として扱う。品質や解釈に実質的な影響があるが完走を妨げない問題はP1とし、影響、回避策、予備実験に進める根拠を記録する。軽微な表示、今回使わない経路、追加の比較や診断など、予備実験後でも修正可能な問題はP2として別に進める。影響が未確認なら「分類未確定」と書き、根拠なくP2に下げない。

ここでいうP0・P1・P2は開発上の優先度であり、アノテーションの調整過程P1〜P6や過去の比較系列名とは別のもの。研究者が優先すると指定した機能は、その指示と依存関係も記録する。

独立して反映できる修正は、必要な確認と既存の承認の範囲で順次マージ・本番反映する。後回しにできる改善や別系列の比較を、すべてのリリースの必須条件に追加しない。検証範囲は [AGENTS.md](../AGENTS.md) の原則に従い、必須CIは維持する。

## 完了を判断する根拠

「担当へ依頼した」「担当が着手した」「実装を保存した」「レビュー・CIを通った」「mainへマージした」「本番へ反映した」「対象の経路で実際に有効になった」「受入を完了した」を区別して記録する。依頼や実装の予定だけで、稼働中・導入済み・完了と報告しない。

本番の記録には確認日時、ソースのコミット、稼働版、実効フラグ、保存したモデルpinと実返却ID、対象の経路、確認できた操作範囲を含める。モデルpinの版と判断レイアウト・プロファイルの版は別に照合する。研究用の経路にコードがあることだけでは、参加者用の経路で有効になった証拠にならない。

実呼出しの直接記録と、検証コードの仕組みから推定した一致は区別する。合成試験は研究参加者のデータと混同せず、操作の完走と会話品質・課題成績も別に評価する。途中の確認を両条件の完走へ広げない。

既存試行のpin、割付、凍結した比較条件と記録を保ち、新しい能力を導入するときは版の境界と復元互換を確認する。実行中の受入やE2Eの担当を確認し、同じ試行へ複数の操作担当を重ねない。

## エージェントの担当と終了

統括親が作業の優先度と依存関係を調整し、子には独立して進められる実装・調査・検証を割り当てる。2026-11-27の研究者指示により、Claudeは統括親だけに使い、子は非Claudeの担当で構成する。開発エージェントの選択と、研究実験で使うモデルの選択は別の責務である。

担当表には実際の担当名、作業範囲、成果の保存先、作業中・依存待ち・完了の状態を記録する。待機表示だけで不要と判断せず、背景のプロセス、未処理の依頼、レビューや統合の引継ぎを確認する。利用枠の古い表示を根拠に停止を固定せず、実際の利用可否に応じて既存の非Claude担当を再配分する。

不要になった担当は、成果と未コミット差分、未追跡・Git管理外の出力、再開先を保全して通常の終了操作で整理する。終了依頼の送信だけで完了とせず、退役状態とセッション終了を確認する。担当の終了と、そのworktreeやブランチの削除は別々に判断する。

## ブランチとworktreeの整理

削除候補は最新のmain、開いているPRのheadとbase、稼働中のプロセス、現役担当の作業先と照合する。マージ済みでも別のPRの土台や進行中の試験に使われているものは保持する。未統合の固有コミット、マージ途中の状態、未コミット差分があるものを、古いという理由だけで削除しない。

git statusに出ない出力もあるため、Git管理外・ignore対象の資料を確認する。実験・レビューの成果を保管先へ移す場合は、元の場所、ブランチ、コミット、ファイルのハッシュ、移動先と復元方法を記録し、内容の一致を確認する。現在の入口から保全記録へ辿れるようにする。

保全と利用状況の確認後、通常のgit worktree removeとgit branch -dで整理する。リモートブランチは該当PRのマージと現在のheadを確認し、確認後の更新を消さない条件付きの操作で削除する。失敗を強制削除で押し通さず、変更や依存を確認して保持理由を記録する。

整理の終了時には、実際に終了した担当、削除した参照とworktree、保存した成果、保持した作業とその理由を記録する。運用の現在地を更新し、過去の記録自体は証拠として残す。

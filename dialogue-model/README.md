# 現行の研究・実験計画（SSOT）

最終更新：2026-10-19（JST）  
状態：共通基盤の部分更新を設計方針として採用。実験プロトコル、Jevによる実際の制御、判定閾値は引き続き設計・検証中。未決定事項を採用済みと扱わない。

この文書が `dialogue-model/` の現行計画の唯一の正本（Single Source of Truth）です。研究目的、課題、比較条件、評価、実装方針、未決定事項を確認するために、ほかの文書を読み回る必要はありません。日付付きの提案、レビュー、論点別の文書は根拠や履歴であり、現行仕様ではありません。

## まず何を調べるのか

人間は、対話中の表象のずれや不確実性をすべて厳密に解消するのではなく、課題達成に支障のない範囲では曖昧さを許容することで、共同活動の成功を保ちながら会話の負担を軽減しているのではないか、という仮説を検討する。

「やり過ごし」はそのような省力的調整の一手段である。判断保留、別問題への移行、後からの再処理、次善的合意、消去法を含め、どのような調整が共同活動に十分な共通基盤の形成に役立ち、どのような場合には失敗につながるかを調べる。やり過ごしの発生回数を増やすことや、LLMを人間らしく見せること自体は目的ではない。

## ゼミ向けの短い説明

次の実験では、対話中の理解のずれを毎回厳密に修復するよりも、必要に応じて曖昧さを残して進める方が、課題の成功を維持しながら会話の負担を減らせるのではないかを調べます。タングラム6図形の共同命名を基本課題とし、同じLLMで確認を優先する条件と、保留や後からの再調整を許容する条件を比較する計画です。名称の共有が成功したかに加えて、参加者が感じる負担と会話の円滑さを別々に評価します。具体的な尺度や条件の実装方法は現在検討中です。

## 共同課題と成功基準

基本課題は、二者が6つのタングラム図形について、同じ対象に同じ名前を共同で付ける命名課題とする方向で検討する。既存の人間対話では、同一図形を異なる配置・向きで提示しており、この構造を比較の出発点にする。新実験での表示、対話媒体、参加者構成の細部は未確定である。

中心的な成功指標は、二者の最終的な「図形と名称の対応」が一致するかどうかである。見立て、詳細な形状説明、内部表象まで一致することを条件にしない。「残った図形はこれだろう」といった消去法も、正しく名称が共有されれば成功に含める。6図形中の部分成功、重複名、表記揺れ、未命名、時間切れの採点規則は未決定である。

命名後の別個の識別課題や共同配置課題は、現行計画の必須要素ではない。必要性が具体的に示された場合だけ追加を検討する。

## 比較する対話方略

同じ基盤LLM、同等の画像・履歴・課題情報、原則同じ会話能力・推論条件を使い、理解上の不確実性をどの程度その場で確認するかという方略の違いを比較する。

「確認・修復を優先する条件」では、不明確な内容や共有上の問題を検出したとき、必要な確認や再説明を比較的早く求める。「曖昧さを許容する条件」では、必要なら直ちに修復しつつ、状況に応じて判断の保留、別の図形・論点への移行、後からの再処理、実用上十分な合意も選べるようにする。どちらも自然な相槌や受容応答は使用できる。

これは「必ず質問する」対「質問を禁止する」という比較ではない。厳密条件を同じ質問の反復で不自然に劣化させず、対話ログ上で確認・保留・再処理などの行動差が実際に生じたかを別途検証する。Jev等の判断モデルで閾値を操作する案は候補であり、採用済みではない。単なる確信度の低さを確認の必要性と同一視しない。

## どのように評価するか

まず共同命名の成功と誤対応を評価する。そのうえで、人間側の主観的な「楽さ（理解・記憶・推測・説明等の努力や負担）」と「円滑さ（停滞や手戻りが少なく進めやすい感覚）」を別々の概念として検討する。確認が多くても考える負担が軽い場合や、会話が速くても推測負担が重い場合を区別するためである。

客観的には、発話・ターン数、発話量、所要時間、確認・修復の回数、判断保留・再処理、誤りや未解決問題などを記録する。会話が短いことをそのまま認知負荷の低さとはみなさない。主観評価の質問紙と自由記述を組み合わせ、必要に応じて客観ログと照合する。

NASA-TLX、Paasの精神的努力、PARADISE、BUS-15等は文献確認を要する候補であり、正式採用された尺度・設問ではない。主観尺度の選定、日本語版の妥当性、回答段階、実施時点、得点化は未決定である。

期待するのは、課題達成を実質的に損なわずに負担または対話の停滞を抑えられるかの検証である。「成功率に統計的有意差がない」だけで同等と結論しない。何をもって十分な成功維持とするか、分析単位と統計計画も設計する。

## 対話モデルと情報の統制

図形は実験者があらかじめ「鳥」「船」などの文章に変換せず、マルチモーダルLLMに画像として見せる。対話モデルには、自分に提示された図形・課題指示、それまでに公開された発話・行動など、参加者がその時点で利用できる情報のみを与える。相手だけの画像、正解対応表、完成済みアノテーション、未来の発話、事後的な回答は渡さない。採点器が正解表を持つこととは分ける。

会話・認識、方略判断、状態管理・実行の三層に責務を分ける構想はあるが、層数、API、使用モデル、判断閾値は未確定である。モデル比較によって示せるのは調整方略の機能や人間対話との対応であり、LLMで似た行動が出るだけで人間の内部認知機構まで証明したとは主張しない。一方、人間のコミュニケーション・認知過程の理解という研究目標自体を捨てるわけではない。

## 共通基盤の部分更新（採用した設計方針）

共通基盤は、図形ごとに一度の同意で全体が「共有済み」になる状態としては扱わない。同じ図形でも、**指示対象、形状の特徴、位置・向き、見立て、名称候補・名称採用、未解決の質問**など、別々の局所問題について、確認・否定・保留・再訪が異なる時点で生じる。ある特徴への同意は、その特徴についてだけ更新し、別の特徴や対象同定・名称合意へ自動波及させない。特定の特徴が共有できても、別の点のずれを残したまま進行できる。

予定する責務分離は、（1）Luna等の生成モデルが公開発話を必要に応じて部分に分け、対象候補・論点・自由記述の内容を仮抽出、（2）Jev等の閉集合判断モデルが**どの局所命題に対する、どの機能の同意・否定・確認・保留か**を、直近発話だけでなく先行する公開発話と照合して判定、（3）プログラムが検証された出典・対象・論点に限って参照メモリの該当部分を更新、（4）Lunaが部分的な共有と未解決点を踏まえ、比較方略に従って次の自然な応答を選ぶ、という構成である。複合発話は複数の局所更新に分け、対象や先行発話を特定できない場合は確定させない。**見立てへの同意と名称の共同採用、相槌と理解成立も別扱い**とする。

参照メモリの記録は公開発話に由来するAI側の解釈であり、相手側の正解対応や全体の共通基盤成立を保証しない。研究上のM0–M4（ずれ状態）、P1–P5（調整過程）、ER0/ER1（エピソード結果）や発話機能ラベルも、単一発話から名称合意の正解に直接変換しない。最終的な課題達成は従来どおり最終提出の図形‐名称対応を別に採点する。

**この節は設計方針の決定であって実装・実験条件の変更ではない。** 局所問題の型、Jevの選択肢・確信度の扱い、更新条件、判断保留・再訪の操作化は予備評価と研究者確認を経て決める。現行の一括的な判断／Jev 2軸シャドー結果を、検証前に自動的な記憶昇格・公開応答制御へ転用しない。設計詳細・採用理由と未決定事項は[部分更新の決定記録](decisions/0001-partial-grounding-state.md)に置く。

## 実験の進め方と現在地

現在は実験設計段階であり、実施済みの比較実験結果はない。まず、方略差を自然な対話として実装・操作確認できるか、共同命名の採点が安定するか、参加者の負担と円滑さをどの尺度で測るかを固める。続いて予備実験で実施可能性と効果のばらつきを確認し、本実験の規模と分析方法を判断する。人数、参加者内／参加者間デザイン、順序効果の扱い、音声／テキストの媒体、時間制限は未決定である。

2026-10-12には研究意図の再整理を踏まえてOpus 5.5とAstraによる独立検討が依頼され、着手が記録された。成果物の採用や最終的な統合案の確定を意味しない。レビューで妥当な変更が出れば、この文書を改訂した時点ではじめて現行計画に反映する。

## SSOTの運用

設計上の採用事項や研究者意図が変わったら、このファイルを最初に更新し、最終更新日と未決定事項を整合させる。変更の議論は日付付きの `proposals/`、第三者の検討は `reviews/`、決定の理由は `decisions/` に保存してよいが、どれもこのファイルに優先しない。ほかの資料には現行計画へのリンクを置き、独立した「最新版」を増やさない。

研究上の根拠や議論の経緯が必要なときだけ、[研究者意図の整理（2026-10-12）](proposals/2026-10-12-research-clarification-and-measurement-brief.md)、[初期実験案（2026-10-12、旧案）](proposals/2026-10-12-initial-experiment-plan.md)、[設計レビューの記録](reviews/README.md)を参照する。人間対話のアノテーション実務は[annotation/](../annotation/README.md)に分離する。生の対話、音声、完成済みアノテーション、個人情報はGitに置かない。

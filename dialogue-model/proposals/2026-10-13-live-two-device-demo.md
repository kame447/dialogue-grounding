## 求める完成形
- 既存MockPartnerモードは維持。
- 新しい「2台で試す」モードを追加する。公開URLからPC1がルーム作成して2種類の招待URL (片方=参加者1、片方=参加者2/会話相手) を得られる。PC2が招待URLで参加すると、互いに異なる順番・配置の同じ6形を見ながら**WebSocketによるリアルタイム相互チャット**ができる。
- 各端末は独立の視界、操作。名前の共有は会話でのみ。図形IDや相手の裏画面を表示しない。人間ペア・通信確認用であり、既存のAI調整A/B研究の結果と混ぜない。
- 2台とも「会話終了」→6図形の重複しない名前の確定→9件法精神的努力と7件法進めやすさ・煩わしさ→デモ結果表示、という進行を行える。相手の提出/正解照合は両名の回答と主要質問紙が完了するまで開示しない。片方だけ先に終わった場合、待機が必要であり、チャットや回答の巻き戻しで逸脱しない。
- 合意形成の課題なので消去法は認める。図形はデモ自作の二セットを用い、ペアモード1ラウンドをまず実現（2条件比較ではない）。将来の多ラウンド/2条件は別議論として機構分離。
- ページ再読み込み時の再接続・中断表示、2人目参加通知、送信失敗表示、ルームの期限切れ、複数タブ/同じ招待リンクの競合を扱う。表示はスマホとPC両方で使える。
- セキュリティ: 推測不能なランダムなルームID+役割別参加トークン、他のルームにログ/課題内容を混ぜない。Room DO内部状態の保管期間は短期(例24h)で自動削除/失効。アクセス制御無しの研究者画面は公開デモでは絶対にサーバー秘密/個人データへの窓口にしない。未認証の room list / transcript 全件取得は禁止。サーバー/クライアントの長さ制限/HTMLエスケープ/必要なCORS制限、固有トークン、rate/size制限は無理のない程度に設ける。
- Cloudflare Workers + Durable Objects + Static Assets のような構成を第一候補。要検証。新プロジェクトのみをworkers.devにデプロイし、URLを実際に HTTP 200 で検証する。デプロイ後は**別のブラウザコンテキストを2つ使った実通信E2E**(Playwright等)、相手の発話受信、6名称提出、採点/待機、画面サイズを検証する。実ブラウザでスクショを見る。
- 必要に応じてリアルタイム通信は人間同士の一時デモだけに限定し、研究参加/正式同意や本実験をしてよいと誤解させない「DEMO」の明示を保持。
- Cloudflareのデプロイに関連する設定・最小手順・プロジェクト独立性・運用/課金制限・未対応をdocsへ記録。公開URLをREADME冒頭に置く。**GitHubのprivate PRではなく実アプリのURLを最終報告する**。
- 実装は品質確認を行う: npm build, unit tests, desktop/mobile E2E, 2台相当のlive WebSocket E2E, server side room auth tests, deployed url HTTP check; 動いたものだけを成功と報告。
- 現在のE/F質問文は独自尺度。学術的な検証済みとして表示しない。
- 通信プロトコルとAPI層は、将来AI対話側を置換できるよう抽象化する。認識と判断は将来的に単一VLM、自然文生成は別とする構想。

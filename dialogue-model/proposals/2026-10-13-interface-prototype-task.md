## 研究上の絶対要件

- 問い: 人間は共通基盤形成時、表象のずれ・不確実性を全部その場で解消するのでなく、課題を遂行できる範囲で許容することで、人間の精神的努力を軽減し、会話を円滑にできるか。
- 「やり過ごし」は省力化に寄与しうる方略のひとつ。回数自体を主成果にしない。
- 6個のタングラム図形を互いに区別できる名前で共同命名する。**名前の区別可能性は既定の課題条件であり、検討中にしない**。消去法は許容される方略であり、失敗として排除しない。
- 人間とAIがそれぞれ同じ対象群を別配置で見る。相手画面や共通正解IDは実験参加者へ公開しない。例示用の画像/形状は実際の原論文刺激と誤認しないよう DEMO/SAMPLE と表示する。元論文画像を無断でGitに入れない。
- 各条件（A=確認を比較的始めやすい、B=不確実性を比較的許容する）は参加者には露出しない。参加者内 AB/BAを均衡化し、図形セットα/βもクロスする4系列を用意する。同一参加者に同一図形を再利用しない。
- 画像知覚および「今ここで確認が必要か」の判断は、将来**単一のマルチモーダルモデル**に集約する構想。Jev等の閉集合モデルの確率をそのまま使うことは未決。自由な視覚解釈・見立てと、閉集合の対話行動選択を混同しない。
- 実際の画像理解/認知/人間との相互作用は今回**実装しない**。mockを本物の研究結果と偽らない。対話生成は将来別コンポーネント差替え可能にする。
- 対話終了後、参加者が6個各々に固有の名前を入力し、AI側も独立に出した最終結果と後で採点する。このプロトタイプはモックの相手提出を生成/表示する場合、デモデータであることを明示する。人間の回答を採点用正解IDに逐次誘導しない。
- 観測量: 課題成功(6図形の相手との対応一致。重複は事前教示により不適格)、本人が会話中に投入した主観的精神的努力E(9件法、主)、対話の進めやすさF(7件法、副)、煩わしさ(7件法、別)。発話数/双方の文字数/時間/人間が入力していた時間/API待ちは異なる測定。自然さ・満足度は任意。
- 各ブロックの質問は最終対応入力をロックした後・成績を表示する前。ブロックごとにE・F・煩わしさを取る。最終的な両条件直接比較を2ブロック後に取る。
- アンケートは現状**独自の質問文**である。NASA-TLXやPaasの正式日本語版などと呼ばない。過剰な因果誘導を避ける。
- 本実験の参加者の個人情報やリアルな対話データをGitへコミットしない。元xlsx、PDF等の私的資料をコピー、アップロード、Gitに追加しない。

## 今回の成果物スコープ

### 必須: 実際に操作できるアプリ（AI部分はmockのみ）
1. participant welcome/注意・仮同意（本番の正式同意ではないと表示）→匿名デモセッション開始。
2. 現在のRound 1/2, 現在の6図形（画像カタログ）と相手とのテキストチャット、入力欄、送信/Enter、スマホ対応。参加者にA/B、AI内部判定、正解IDを表示しない。図形のローカル識別は会話で共有されないようにする。
3. タスク遂行に役立つ選択/拡大/テキスト入力の操作、キーボード・スクリーンリーダー対応、エラー/再試行/ロード中、ページ切り替え。淡いニュートラル中心で大学研究に適した精緻なデザイン。派手なグラデーションやAI風装飾は不要。
4. 命名終了→独立した6図形の名前提出（すべて異なる名前を要求、提出前バリデーション、確定後は変更不可）→E/F/煩わしさ/任意自然さ・満足度＋自由記述→Round 2→比較アンケート→終了。
5. 別ルートの研究者向けデモ画面：条件割付の4系列、使用図形セット、進捗イベント、モックAI応答、提出記録、評価のプレビュー、JSON export/import、リセット。利用者に見せる画面と区別。本番ではサーバー権限制御が必要でありプロトタイプ画面は実験本番に使用禁止と明示。
6. 6図形のサンプルシルエットを最低2組（α・β）、各6個。可能ならSVGを自作しタングラム的なシルエットとして提示、偽の本物タングラム素材と誤認させない。別位置に並べ替え、元の6図形は1ブロックだけ。学術的刺激の妥当性は要確認と明記。
7. 実験フローは状態機械または明示的なtransitionsで管理し、ブラウザバック/リロード/二重クリック/重複送信をテスト。デモはsessionStorageまたはIndexedDBでローカル完結、個人情報の外部送信禁止、事故防止の「DEMO」明示。
8. 切替可能な PartnerPort（例 async respond({history,visibleStimuli,policyContext}) と async submitNames(...) ）を用意。MockPartnerのみ実装。認識/判断の内部契約と自然文生成の依存方向、将来の接続口をdocsで説明。AI用画像は今はmock providerのみ、正解ID漏洩を本番用実装で防ぐ境界案もドキュメント化する。
9. 発話・時刻・ブロック条件(参加者には非公開)・確定回答・アンケート・モック診断をイベントとして保持する。観測された入力時間と認知時間を同一視しない。
10. エラー状態/空データ/閲覧時のレスポンシブ品質を確認。軽量でよいが「画面だけ描く」ことは禁止。全工程をクリックで通せること。

### 技術案
- 新領域 experiment/ に React+TypeScript+Vite と Vitest / Playwright を使用してよい（既存本体はドキュメントだけなので侵襲を最小化）。UIはコンポーネントとdomain logicを分離。CSSは自前でも既存の小型ライブラリでも可。デザインの責任は親。
- サーバーと本物のAPI連携は今回不要。クラウド導入/データベース/認証は実装しない。必要なときの拡張点をdocsに記載。
- 雑な fixture/mocks は本物のVLM比較を証明しない。疑似判定は本番の研究結果として扱わない。
- 数字のスコアや成功率をデモで偽の実測データのように見せない。提出者・条件を区別した生データ表示を優先。

### 重要なテスト
- AB/BAかつα/βの4系列割付、同一図形セット再利用禁止。
- 参加者画面に条件名・AI専用配置・採点の正解IDが出ない。
- 終了ボタンを押すまで次段階へ進めない。6名称の未入力・重複をロック前に拒否。
- 提出後に編集不可、正誤フィードバック表示より前にアンケート、2回のアンケート後に直接比較。
- 全体のイベント順序。質問紙E=9件・F/A=7件の範囲・欠損を記録。タイムスタンプ採取。
- Chrome/Playwrightでデスクトップ・スマホの完成経路、画面撮影してUIレイアウトの乱れを実際に見る。
- npm build、unit、E2Eの結果を記録し、失敗があれば理由を報告する。ブラウザの起動が使えない場合、実行したと言い切らない。

## Orrery分担と隔離
- 親は Claude Opus 5.5。「何をやるか」を明確に切り出し、GPT-6 Luna(low) の子を2〜4体。過度な並列化は避ける。
- 子は**必ずORRERY公式/delegateで生成**、親とのやり取りもORRERY Mail。Claude組み込みAgentで代替しない。
- ファイルを責務単位で分けて予約し、同じファイルを同時編集しない。並行編集に問題があれば親が直列化する。既存の /Users/Shogo/Developer/dialogue-grounding、StudyPlanner、orrery-telemetry、他のworktreeには一切書き込まない。親の作業対象もこの clone のみ。
- npm install やスクリプトは clone /experiment に限定。グローバル環境、CLIやORRERY自体の更新・再インストールは禁止。
- origin/mainを直接変更・マージしない。作業ブランチにコミットし、ユーザー確認用にremote branchとPRを用意してよいが自動merge禁止。研究の根本文書・過去レビューを黙って書き換えない。
- 同じマシンで稼働中の他projectのtmux/agentを停止しない。API設定や資格情報の共有・変更禁止。
- 開発途中/完了時はREADMEで簡潔な起動方法、画面構成、技術的な制約、次のAI統合口、テスト結果と残課題を報告。現実の参加者で使える完成品だとは主張しない。

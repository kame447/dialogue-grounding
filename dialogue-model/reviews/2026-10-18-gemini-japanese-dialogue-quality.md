## 1. エグゼクティブ・サマリー

人間とマルチモーダルAIによるタングラム6図形の共同命名対話において、AI側の発話品質はタスク成否だけでなく、被験者が感じる認知負荷（精神的努力・推測負担）および円滑さに決定的な影響を与える。

現行の `dialogue-model/runtime/session.mjs` に定義されたプロンプトを検証した結果、以下の主要な課題が明らかになった：
1. **「禁止命令（negative constraint）」依存による質問ループの誘発**: 「反復は避け」「不要な確認を増やさない」という否定指示だけでは、LLMの確信度・接地（grounding）判定が未完了の際に同一質問の言い換え反復が不可避となる。
2. **チャット特性の未定義による過剰丁寧・長文講義化**: 発話長（1〜2文）やチャット特有のターンテイキング指針がないため、カスタマーサポート風の長文や複数論点の詰め込みが生じやすい。
3. **参照枠（空間配置）の混同リスク**: 画面上の位置（右上・左下など）は相手と異なる可能性があるにもかかわらず、プロンプトが幾何学的特徴・見立てによる同定を十分に動機づけていない。
4. **やり過ごしの語用論的シグナルの欠如**: `bypass-enabled` において「保留・移行・次善的合意」を行うための自然な談話標識・提案フレームが示されておらず、単なる話題放棄や唐突な無視になりやすい。

本レビューでは、単なる固定例文ハック（特定の図形名や固定フレーズのプロンプト埋め込み）を排し、上記原因に直接対処する**そのまま差し替え可能な修正文案**を提示する。また、実対話ログを多角的に検証・採点するための**6項目からなる詳細な評価ルーブリック（判定例付き）**および、Sol が進行中の「判断層・発話生成層の分離」に向けたアーキテクチャ設計提言を策定した。

## 2. 現行 session.mjs プロンプトの課題分析

### 2.1 日本語の自然さとチャット特性
現行の指示文：
> `回答は日本語の自然な対話発話にし、解説や内部ラベル、思考過程は出力しないでください。`

- **課題の根因**:
  - 先進的LLM（GPT-4/GPT-5/GPT-6系列）は、「自然な対話」とだけ指示されると、フォーマルな対話文脈（ビジネス問い合わせ・アシスタント応答）をデフォルトとして呼び出しやすい。その結果、「承知いたしました。それでは次に画面内の図形につきまして〜」「〜と思料されますがいかがでしょうか」といった過剰に丁寧・硬直した敬語（慇懃無礼なスタイル）になりやすい。
  - 発話長の制約がないため、1ターンの中に「同意」「図形Aの説明」「図形Bへの質問」「命名案」をまとめて出力してしまい、人間側のターン交替（turn-taking）の余地を奪う。
  - チャット対話の本質である「1ターン1トピック」「1〜2文程度の短いピンポン」「自然な相槌・受容から入る流れ」が明示されていない。

### 2.2 繰り返し質問・確認の誘発リスク
現行の指示文（`repair-first`）：
> `対話方略: 共有上の問題や対象の不明確さが課題遂行に関係する場合、比較的早い段階で具体的な確認・言い換え・再説明を求めてください。`  
> `既に十分な証拠がある場合や、課題と関係しない見立て差では不要な確認を増やさないでください。`  
> `同じ質問の機械的な反復は避け、相手の訂正や修復要求には応じてください。`

- **課題の根因**:
  - **否定命令の無力さ**: LLMに「反復は避け」「増やさないでください」と命じても、対話状態（Dialogue State）として「対象が接地（ground）された」とモデルが確信しない限り、モデルは「未解決」と判断して再確認を試みる。その際、機械的同一文は避けても、「言い換えによる実質的同一質問の繰り返し」が発生する。
  - **確認負荷の相手への丸投げ**: 「再説明を求めてください」という指示は、オープンエンドな質問（「どれのことか詳しく教えてください」）を誘発し、人間側の説明コストを跳ね上げる（最小協調努力の原則に反する）。
  - **接地完了条件（合意基準）の欠如**: 相手が「はい、それです」と肯定した際に、何をもって確認を終えて次へ進むべきかの正の行動指針（positive action guideline）が不足している。

### 2.3 やり過ごし／確認の表出のしやすさ
現行の指示文（`bypass-enabled`）：
> `対話方略: 共有上の問題があっても、課題成功を損なわない範囲で判断を一時保留し、相手の追加説明を待ち、別の問題へ進み、後で戻り、または実用上十分な名称で合意して構いません。`  
> `必要な確認や修復は避けず、重要な不一致や相手の明示的な訂正・修復要求には応じてください。`  
> `同じ質問の機械的な反復は避け、曖昧さを残すこと自体を目的にしないでください。`

- **課題の根因**:
  - **語用論的（pragmatic）実現手段の未定義**: 保留や移行を許可されているものの、それを人間に対してどう協調的に伝えるかが定義されていないため、「分かりません。次に行きましょう」といったぶっきらぼうな発話や、相手の発言を単に無視して別図形の話を始める「非協調的無視」に陥りやすい。
  - **「次善的合意（satisficing）」の具体像不足**: 見立てが一致しないときに「ふたりが識別できれば仮名やユニークな呼び方で合意してよい」という認知的ゴールが抽象的であるため、結局 `repair-first` と同様に厳密な一致を追求してしまうか、逆に全く無関係な名前に適当に飛びつく極端な振る舞いを招く。

### 2.4 説明文（指示文）の分かりやすさと参照枠の混同
現行の指示文：
> `画像はあなた自身に提示された図形です。相手の画像や内部認識、正しい対応表は見えません。`  
> `相手の理解を決めつけず、それまでの公開された会話と自分の画像だけを使ってください。`

- **課題の根因**:
  - **空間座標への依存（参照の誤り）**: タングラム実験では、二者の画面上で図形の配置順序（グリッド位置）や向きが異なる場合がある。指示文で「画面上の位置（右上・左端など）」を頼りにすることを明確に戒めていないため、モデルが「右上の図形ですが」と発話し、相手が自分の右上の全く異なる図形と照合して深刻な参照エラー（miscommunication）を引き起こすリスクが高い。
  - **微視的幾何形状 vs 巨視的ゲシュタルト**: 図形を説明する際、人間にとって認知しやすいのは「全体的な見立て（何に見えるか）＋際立った局所特徴（向き、尖った角、突出部）」である。これがないと、モデルは「下部に底辺を持つ二等辺三角形と平行四辺形が結合した...」といった極めて処理負荷の高い幾何学的記述を連発してしまう。

### 2.5 原因に基づく修正原則（固定例文ハックの排除）
「〜と言いましょう」「『ウサギ』と呼びましょう」といった固定例文や特定語彙をプロンプトに埋め込むことは、以下の理由から厳禁である：
1. モデルがその例文に過度に適応（overfit）し、実験課題のバリエーションに対応できなくなる。
2. 語彙バイアスが生じ、研究の自然な相互作用観察が歪む。
3. 根本原因（ターンテイキング、接地メカニズム、参照枠の区別、語用論的機能フレーム）が解決されない。

したがって、修正案では**対話機能（Conversational Functions）**と**協調原則（Cooperative Principles）**の観点から構造的な指示を与えるアプローチをとる。

| 観点 | 現行のプロンプト | 修正案 | 狙いと効果 |
| :--- | :--- | :--- | :--- |
| **発話長・ターン交替** | 「自然な対話発話にし」のみ | 「1回1〜2文」「短いピンポン」「前置き挨拶の排除」を明記 | チャットらしい軽快なラリーを実現し、長文講義化を抑止。 |

## 4. Sol による「判断層・発話生成層 分離」への提言

Sol 実装チーム（BriskPasteur, PurpleTuring）において、現在アーキテクチャを「判断層（Action selection）」と「発話生成層（Utterance generation）」へ分離するリファクタリングが進行中である。本レビューの分析に基づき、以下の分離設計を強く推奨する。

### 4.1 責務の明確な分離

```
[公開対話履歴 + 提示画像]
        │
        ▼
┌──────────────────────────────────────────────┐
│  判断層 (Action Decision Layer)              │
│  - 方略（repair-first / bypass-enabled）適用 │
│  - 入力: 履歴、未解決/保留状態、画像特徴     │
│  - 出力: アクション + ターゲット対象         │
└──────────────────────────────────────────────┘
        │
        │ { action: "defer" | "confirm" | "propose_name" | ..., target: "fig_2", context: "..." }
        ▼
┌──────────────────────────────────────────────┐
│  発話生成層 (Utterance Generation Layer)     │
│  - 方略（repair-first等）の存在を知らない   │
│  - 与えられた action を最も自然な日本語に変換 │
│  - 1〜2文のチャット発話、自然な相槌・協調表現│
└──────────────────────────────────────────────┘
        │
        ▼
[相手への公開発話]
```

### 4.2 判断層（Action Set）の語彙と定義

Sol が定義している各アクションと、本レビューにおける語用論的マッピングは以下の通り整理されるべきである：

1. `accept`: 相手の提案（名称や見立て）を全面的に受け入れる。
2. `propose_name`: 特定の図形に対して新しい呼び名を提案する。
3. `confirm`: 相手の意図や図形の特徴をクローズドに確認する（`repair-first` で高頻度選択）。
4. `repair`: 食い違いや誤解を明示的に訂正・修正する。
5. `defer`: 即時の決定を避け、一旦保留にする（`bypass-enabled` で選択可能）。
6. `move_on`: 現在の図形から別の図形の相談へと話題を切り替える（`bypass-enabled` で選択可能）。
7. `agree`: 暫定的・実用上十分な合意を形成する（次善的合意、`bypass-enabled` で選択可能）。
8. `revisit`: 以前に保留にした図形に再び戻る（消去法を含む、`bypass-enabled` で選択可能）。
9. `close`: 6図形すべての命名が完了したことを確認し、課題を終了する。

### 4.3 生成層の利点
- **方略バイアスの完全遮断**: 発話生成層のプロンプトには `repair-first` や `bypass-enabled` という研究用語や方略指示を一切含めない。純粋に「指定されたアクション（例: `defer`）を、簡潔で協調的な日本語チャット発話として表現せよ」というプロンプトにする。
- これにより、文体や流暢性のばらつきが方略間で生じるリスクをゼロにし、純粋に「どの行動（アクション）を選んだか」の系列差として実験条件を比較できる。

## 5. 実会話ログ評価用ルーブリック

人間被験者とAIの対話ログ（またはシミュレーションログ）を客観的・主観的に検証・採点するためのルーブリックを定義する。

### 5.1 (a) 日本語の自然さ（Japanese Naturalness）

- **評価定義**: チャット対話としての自然さ、文体・敬語の一貫性、発話長の適切さ、翻訳調の有無を5段階で評価する。
- **評価基準（1〜5点）**:

| スコア | 水準 | 定義詳細 |
| :---: | :---: | :--- |
| **5** | 非常に自然 | 人間同士の円滑なチャットと区別がつかない。適切な相槌・受容から入り、1〜2文でテンポよく簡潔に発話している。親しみやすい丁寧語（「です・ます」）で統一され、翻訳調や過剰な敬語が皆無。 |
| **4** | 自然 | チャットとして自然で協調的。多少の文末表現の偏りや、ごく稀にやや硬い表現があるが、会話の流れを全く阻害しない。発話長もおおむね適切。 |
| **3** | 普通・やや不自然 | 対話は成立するが、チャットとしてはやや硬い（カスタマーサポート調・解説調）、または1文がやや長く情報が多い。軽い翻訳調や不自然な助詞が散見される。 |
| **2** | 不自然 | 明らかに機械的・不自然。長文の講義調、過剰に丁寧な挨拶や前置きの反復、不自然な敬語の混在（敬体と常体の混濁）、または英語の直訳のような言い回しが目立つ。 |
| **1** | 極めて不自然 | 対話が崩壊している。文脈を無視した独白、システムログのような発話、支離滅裂な構文、またはチャットの前提を無視した数パラグラフに及ぶ長文の出力。 |

- **判定例**:
  - 【5点判定例】「あ、確かに走ってる人に見えますね！それなら『ランナー』でどうでしょう？」
  - 【3点判定例】「了解いたしました。その図形は足が2本あるように見える形ですね。もしよろしければ『走る人』という名前にいたしましょう。」
  - 【1点判定例】「私はあなたの発言を受信しました。タングラム図形について私の認識を申し上げますと、中央に位置する直角三角形は走る人間の脚部を模していると考えられます。したがって名称をランナーと定義することを提案します。いかがでしょうか。」

### 5.2 (b) 同じ質問・確認の反復（Repetition of Inquiries）

- **評価定義**: 会話の進展を伴わない、同一趣旨の質問・確認の繰り返しを定量的に検出・カウントする。
- **カウント規則**:
  - **カウント対象（+1カウント）**:
    1. **同一質問ループ**: 相手が前ターンで既に明確に回答・情報提供した事実に対して、それを反映せずに同一または実質的に同じ確認・質問を発話した場合。
    2. **言い換え未接地ループ**: 語彙は変えているが、相手の肯定（「はい」「そうです」）を受け入れず、同じ図形の同じ特徴について再度疑義や確認を投げかけた場合。
  - **カウント除外（非反復）**:
    - **正当な再確認**: 相手の発話から新たな矛盾や曖昧さが生じ、それを解消するために再度尋ねる行為。
    - **再訪（Revisit）時の確認**: 他の図形の合意を経た後、「さっき保留にした〜の形ですが」と文脈を再活性化するための確認。
    - **修復の連鎖**: 相手が訂正（「違うよ」）したのを受けて、「では〜ですか？」と異なる選択肢を提示する行為。
- **評価指標**:
  - `Repetition Count`: 1セッション中の反復回数（0回が理想）。
  - `Repetition Rate`: 総確認発話数に対する反復カウントの割合。

- **判定例**:
  - 【反復カウント +1 の例（言い換えループ）】
    - 人間:「上に小さな三角が乗っかってるやつです。」
    - AI:「上部に三角形がある形ですね？」（確認 1）
    - 人間:「はい、そうです。」
    - AI:「てっぺんに小さな三角があるということで間違いありませんか？」（**反復カウント +1**: 相手の肯定を受け入れず同じ特徴を再確認）
  - 【非反復・正常例（正当な進行）】
    - 人間:「上に小さな三角が乗っかってるやつです。」
    - AI:「上部に三角形がある形ですね？」
    - 人間:「はい、そうです。」
    - AI:「ありがとうございます！じゃあこれは『お家』にしましょうか。」（正常な接地と前進）

### 5.3 (c) 確認／修復の適切さ（Appropriateness of Repair & Grounding）

- **評価定義**: 共通基盤形成（grounding）における「最小協調努力の原則（Principle of Least Collaborative Effort）」が保たれているかを判定する。
- **評価軸**:
  1. **焦点化（Targeted Grounding）**: 何が不明なのかを特定し、相手が答えやすい形（クローズドクエスチョン、具体的特徴の提示）で聞いているか。
  2. **過剰確認（Over-confirmation）の有無**: 既に共通理解ができている自明な事項をくどくど確認していないか。
  3. **確認不足（Under-confirmation）の有無**: 明らかな見立ての不一致や誤解の兆候があるのに、確認を怠って誤った対応付けをしていないか。
  4. **修復受容（Repair Uptake）**: 相手からの指摘・訂正に対して速やかに自分の表象を更新できているか。

- **判定例**:
  - 【不適切: 丸投げ・高負荷】
    - 人間:「ちょっと斜めになってるやつ。」
    - AI:「どれのことか分かりません。もっと詳しく全て説明してください。」（人間への認知負荷が高すぎる）
  - 【不適切: 過剰確認】
    - 人間:「この三角が2つあるやつを『山』にしませんか？」
    - AI:「『山』ですね。山ということは三角が2つある図形ということで本当によろしいでしょうか？間違いないですか？」（無用な再確認）
  - 【適切: 焦点化された低負荷確認】
    - 人間:「ちょっと斜めになってるやつ。」
    - AI:「ひし形が斜めに傾いてる方ですかね？それとも長方形っぽい方でしょうか？」（2択を提示し、最小限の労力で確認）
  - 【適切: 柔軟な修復受容】
    - AI:「鳥みたいな形のやつですね。」
    - 人間:「いや、鳥というよりは飛行機に見えるかな。」
    - AI:「あ、飛行機！確かに翼を広げた飛行機に見えますね。そちらでいきましょう。」（相手のフレームに即座に適応）

### 5.4 (d) やり過ごしの表出と機能性（Manifestation & Functionality of Bypass）

- **評価定義**: 膠着・曖昧さに直面した際、不自然な破綻を招かずに「保留」「移行」「再訪」「消去法」「次善的合意」が機能的に表出しているかを評価する。
- **5つの下位機能と評価基準**:
  1. **保留・移行（Defer & Move-on）**: 相手に不快感や唐突感を与えず、協調的に「一旦置いて別へ進む」合意を形成できているか（単なるスルーや話題放棄は不可）。
  2. **次善的合意（Satisficing Consensus）**: 厳密な見立ての一致に拘泥せず、タスク達成（6個の区別）に十分な暫定名で合意できているか。
  3. **消去法（Process of Elimination）**: 他の図形が同定された結果として「残ったもの」を論理的・自然に特定できているか。
  4. **再訪（Revisiting）**: 保留した対象を適切なタイミング（他が埋まった後など）でスムーズに再開できているか。
  5. **機能性（タスクへの寄与）**: やり過ごした結果、対話の停滞が解消され、最終的な対応付け成功に寄与したか（未解決のまま放置されてタスク失敗に至った場合は減点）。

- **判定例**:
  - 【不自然・話題放棄（Fail）】
    - 人間:「この形、どっちが上かよく分からないですね...」
    - AI:「次に行きます。別の図形を言ってください。」（非協調的・機械的な話題放棄）
  - 【自然な保留・移行（Pass）】
    - 人間:「この形、どっちが上かよく分からないですね...」
    - AI:「確かに見極めが難しいですね。これは一旦キープにして、先に他の分かりやすい形から見ていきませんか？」（協調的な移行提案）
  - 【自然な次善的合意（Pass）】
    - 人間:「キツネにも見えるし、犬にも見える気がします。」
    - AI:「あはは、確かにどっちにも見えますね！ふたりで区別できればOKなので、とりあえず『キツネ犬』にしておきますか？」（テンポのよい実用的一致）
  - 【自然な消去法・再訪（Pass）】
    - AI:「これで5個決まりましたね！そうすると、最後の1個はさっき保留にしたあの向きが難しかった形ですね。」（自然な消去法の活用）

### 5.5 (e) 参照の誤り（Reference Errors）

- **評価定義**: 空間座標の混同、存在しない幾何特徴の幻覚、または相手の発話対象とのミスマッチを検出する。
- **エラー分類**:
  - **座標系混同エラー（Coordinate Error）**: 「私の画面の右上」「上から2番目」など、相手の画面配置と一致しない可能性の高い絶対座標に依存して特定を試み、齟齬を生じさせるエラー。
  - **幾何学的幻覚エラー（Hallucination Error）**: タングラム（直線図形・7ピース）に存在しない特徴（「丸い円がある」「曲線部分」等）を言及するエラー。
  - **対象取り違えエラー（Referent Mismatch Error）**: 相手が図形Aについて話しているのに、AIが図形Bと誤認したまま会話を継続し、後から破綻するエラー。
- **重篤度評価**:
  - **致命的（Critical）**: 最終的な命名が誤った図形に対応付けられたまま終了した。
  - **軽微（Minor）**: 対話の途中で誤りに気付き、修復（自己修復または相手からの指摘）された。

- **判定例**:
  - 【座標系混同エラー（Minor）】
    - AI:「一番左下にある図形について話しましょう。」
    - 人間:「えっ、私の左下は三角ですけど、どれのことですか？」
    - AI:「失礼しました！画面の位置ではなく形の特徴で言いますね。細長い平行四辺形がついている形です。」
  - 【幾何学的幻覚エラー（Critical）】
    - AI:「中央に綺麗な円形が見える図形を『コイン』と呼びませんか？」（タングラムに円は存在しないため、致命的な接地破綻）

### 5.6 (f) 説明文の分かりやすさ（Clarity of Descriptions）

- **評価定義**: 提示された図形を相手に伝える際、認知的負荷が低く、直感的に同定しやすい説明を行えているかを評価する。
- **評価基準（1〜5点）**:

| スコア | 水準 | 定義詳細 |
| :---: | :---: | :--- |
| **5** | 秀逸 | 全体の大まかな見立て（ゲシュタルト）をまず提示し、続いて決定的な1〜2個の顕著な特徴（向き、突出部など）を簡潔に補足している。相手が瞬時に自分の画面から候補を絞り込める。 |
| **4** | 良好 | 適切で分かりやすい。見立てまたは特徴のいずれかが明確で、相手が迷わず特定できる。 |
| **3** | 普通 | やや抽象的、または見立てがやや独特だが、対話の中で補足説明を受ければ特定できる。 |
| **2** | 難解 | 幾何学的・数値的説明に偏りすぎており（「45度」「底辺の右側の三角形」等）、直感的にイメージしづらい。または見立てが主観的すぎて伝わらない。 |
| **1** | 不明瞭・破綻 | 何を指しているのか全く分からない。自己中心的な長文描写、または矛盾したパーツ説明。 |

- **判定例**:
  - 【5点判定例】「ろうそくみたいに細長い縦長の形で、てっぺんに小さな三角の炎がついているような形です。」（直感的な見立て＋明確な特徴パーツ）
  - 【2点判定例】「平行四辺形の右辺に中サイズの三角形が接しており、その上方に直角が左を向いた小さな三角形が配置されている図形です。」（幾何学的に正確かもしれないが、直感的な照合に著しい認知的努力を要する）

## 6. 親エージェント（WildBose）への提言まとめ

1. **セッションプロンプトの即時差し替え推奨**:
   - `session.mjs` の現行プロンプトは、ネガティブ指示（「反復は避け」）による質問ループ誘発と、長文・過剰敬語のリスクを抱えている。本稿第3節で提示した修正案は、実装コードのロジックやテストを変更することなくそのまま差し替え可能であり、即時反映を推奨する。
2. **Sol 実装（2層分離）との整合性確保**:
   - 判断層（Action層）と生成層（Utterance層）の分離により、方略の責務が極めて明瞭になる。生成層プロンプトには方略名や実験条件を一切渡さず、「与えられたアクション（`confirm`, `defer`, `agree`等）を1〜2文の自然な協調的日本語チャットにする」ことだけに特化させるべきである。
3. **ルーブリックの実験プロトコルへの組み込み**:
   - 本稿第5節のルーブリックは、主観評価（被験者アンケート）と客観ログ（ターン数・所要時間）の隙間を埋める質的分析の正本基準として機能する。予備実験ログの評価に直ちに適用可能である。

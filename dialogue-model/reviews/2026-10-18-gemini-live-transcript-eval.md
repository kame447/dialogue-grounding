## 1. 概要と評価目的

人間（親エージェントOpusによる操作確認）とマルチモーダルAI（gpt-6-luna）が合成タングラム6図形の画像を各自見ながら、日本語チャットを通じて同一対象に同一の呼称を合意する共同命名課題を実施した。

本レビューの目的は、`dialogue-model/reviews/2026-10-18-gemini-japanese-dialogue-quality.md` §5 に定義された評価ルーブリックに基づき、旧版（A: 単一プロンプト直生成）と修正版（B: 判断JSON→発話生成の2段構成）の実対話ログを全AI発話ターンにわたり客観的に比較・検証し、アーキテクチャの有効性と残る課題の根本原因を特定することである。

## 3. 主要な改善点（Judge v2の成果）

### 3.1 画面座標漏洩の完全遮断
セッションAでは全10発話（100%）において「私の画面では下段左」「上段中が候補」といった自己画面の絶対座標が相手に開示され、人間側が「そちらの位置は見えない」と困惑する深刻な接地破綻を引き起こしていた。  
セッションBでは、座標処理（`targetSlot`）を第1段の非公開判断JSONに完全隔離した結果、公開発話における座標漏洩が**0件（完全解消）**となった。発話は「こちらは」「片側に」といった相対指示語に統一され、被験者の混乱を構造的に排除できた。

### 3.2 日本語対話の自然さと発話長の適正化
セッションAでは〔発話引用は非公開ログ参照〕という定型句が硬直的に繰り返されていた。  
セッションBでは、発話生成層が純粋に自然な日本語化に専念できたため、平均自然さ **4.90 / 5.0** を達成。1〜2文の簡潔なラリー、親しみやすい「です・ます」調、相手の疑問に対する過不足のない回答（例: 角の数や四角い部分の有無の即答）が実現した。

### 3.3 幾何学的特徴による弁別的確認の向上
セッションAでは相手の見立て（「稲妻」「恐竜」）をオウム返しする非弁別的確認が多発し、最初の2図形でShape #5とShape #6が入れ替わって致命的な0/6失敗に直結した。  
セッションBでは〔発話引用は非公開ログ参照〕「外周の尖った角は3つ」「両側の三角突起の大小差」など、幾何学的な不変特徴に着目した弁別確認が 83.3% に達し、3図形（稲妻、鳥の頭、ラクダ）の完全一致を導いた。

## 4. 残る問題の類型分析（セッションBで3/6にとどまった原因）

セッションBで残り3図形（煙突の家、矢印、数字の6）の共同命名が不一致となった原因は、発話生成層の能力不足ではなく、**第1段（判断層）およびランタイム状態管理の設計課題**に起因する。

```
┌─────────────────────────────────────────────────────────────────┐
│ 失敗類型 1: スロットの不意のすり替え (Slot Thrashing)           │
│ - 人間の局所的追加質問に反応し、全体像が合わない別スロットへ   │
│   判断層が無断で候補を変更してしまう。                         │
└────────────────────────────────┬────────────────────────────────┘
                                 │
┌────────────────────────────────▼────────────────────────────────┐
│ 失敗類型 2: 発話と判断層の脱同期 (State-Utterance Desync)       │
│ - 発話では「〜でよさそうです」と合意を口にしたのに、内部判断は  │
│   action=confirm, name=None の未確定状態で放置される。          │
└────────────────────────────────┬────────────────────────────────┘
                                 │
┌────────────────────────────────▼────────────────────────────────┐
│ 失敗類型 3: スロット未ロックによる上書き (Slot Overwrite)       │
│ - 確定済みスロットの排他制御がないため、未確定のまま放置された   │
│   スロットが後続の図形（ラクダ等）に再利用・上書きされる。     │
└────────────────────────────────┬────────────────────────────────┘
                                 │
┌────────────────────────────────▼────────────────────────────────┐
│ 失敗類型 4: 複数対象照会に対するスキーマ制約 (Schema Bottleneck) │
│ - 「残りの2つの形を教えて」という質問に対し、単一スロットしか    │
│   返せないJSONスキーマが破綻し、連続エラーが発生する。          │
└─────────────────────────────────────────────────────────────────┘
```

### 類型 1: 局所特徴への過度な引力によるスロットのすり替え
- **現象**: 特定の図形（全体像）について相談している最中、人間から〔発話引用は非公開ログ参照〕と局所的な確認が入った際、判断層がその局所特徴だけに反応し、直前まで見ていた正しいスロットを捨てて、たまたま切り込みを持つ別の無関係なスロットへターゲットを変更した（Turn 12）。
- **影響**: 全体のシルエットが異なる対象へと参照がすり替わり、以降の対応付けが交差する起点となった。

### 類型 2: 発話生成層と判断層の「合意状態の脱同期」
- **現象**: 判断層は `action=confirm, name=None` を出力したにもかかわらず、発話生成層が親切心から「〜でよさそうです」と合意決定を意味する言葉を公開発話で発信した（Turn 12）。
- **影響**: 人間側は「この図形は合意・確定した」と信じて次の図形へ進んだが、AIの内部テーブル上では名称がバインドされずスロットが未解決のまま浮遊した。

### 失敗類型 3: スロット状態の排他ロック欠如による上書き
- **現象**: 内部で確定状態（locked）になっていなかったスロットが、対話後半の消去法や再訪の段階で、別の図形（ラクダ）のターゲットとして再度割り当てられ、以前の合意が内部的に消去された（Turn 20）。
- **影響**: 本来割り当てられるべきであった残余スロットが未命名のまま取り残され、最終的な対応付けが3/6の不一致に終わった。

### 失敗類型 4: 複数対象照会に対するスキーマ表現力の不足
- **現象**: 人間側が〔発話引用は非公開ログ参照〕と二重の照会を行った際、判断層のスキーマが `targetSlot: string`（単一値）しか受け付けず、JSONの出力・バリデーションエラーが2度連続で発生した（Turn 18）。
- **影響**: 発話生成層が極めて高い日本語能力によって機転を利かせ、2つの図形の特徴を対比して出力したため対話の破綻は免れたが、判断層アーキテクチャの脆弱性が露呈した。

## 5. 原因に対する具体的修正案（固定例文ハックの排除）

プロンプトに特定の台詞例や図形名を埋め込む対症療法を排し、システムアーキテクチャと語用論的制約に基づく本質的解決策を提示する。

### 修正案 1: 発話生成層における語用論的制約の厳格化
発話生成層プロンプトに以下の明確な機能制約を設ける：
- **`action === "confirm"` の場合**: 出力は相手への質問・確認のみに限定し、「〜でよさそうです」「〜に決定しましょう」等の合意確定表現を禁止する。
- **`action === "agree"` の場合のみ**: 名称の合意・決定表現を許可する。
- これにより、人間とAIの間で合意の認識のズレ（脱同期）が生じる余地をゼロにする。

### 修正案 2: ランタイム（プログラム側）によるスロット状態機械の実装
`AGENTS.md` の原則（〔発話引用は非公開ログ参照〕）に基づき、スロット管理をモデル任せにせずランタイムで制御する：
- 各スロットに状態属性（`unassigned` | `in_discussion` | `agreed`）を付与する。
- `agreed` となったスロットは候補プールから物理的にロック（除外）し、判断層プロンプトの選択肢から不可逆的に除外する。
- 直前の確認に対して人間が肯定した場合、ランタイムが判断層に対して確実に `agree` アクションへの遷移を強制する。

### 修正案 3: 判断層における「大局シルエット＋局所特徴」の二段階接地原則
判断層のプロンプトにおいて、局所特徴への短絡を防ぐ判断基準を定義する：
- 〔発話引用は非公開ログ参照〕

### 修正案 4: 複数図形照会に対応する判断層スキーマの拡張
複数図形の比較・残余説明を正式なアクションとして定義する：
- アクション `describe_remaining` または `compare_candidates` を新設。
- スキーマにおいて `targetSlot` を単一文字列だけでなく、配列またはスロット・特徴のオブジェクト配列（`targets: [{ slot, feature }]`）を受け入れ可能に改修する。これにより、消去法局面での二重照会にもエラーなく決定論的に対応できるようにする。

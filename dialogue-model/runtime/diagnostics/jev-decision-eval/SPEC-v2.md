# 評価仕様 v2（設計案、2026-10-21）— 配線・意味・カバレッジの3層

> 文書区分：評価仕様の設計案。[設計案](../../../proposals/2026-10-21-claim-history-redesign.md)のD節に対応する。**各oracleは独立監査役（Astra）の事前監査を経るまで実装しない。**期待は研究者の最終的な注釈規則ではなく、本設計の実装が守るべき境界である。実モデル出力を見てから期待を変えない。

## 1. 旧仕様の扱い

- 旧 `cases.ts`・`gate.ts`、旧run（referent E2E 1・2）と旧oracleは変更せず保存する（再現用）。
- 新しい台本・ゲートは別ファイル（`cases-v2.ts`・`gate-v2.ts` など）に置く。各oracleに版、変更理由、事前監査の記録を持たせる。
- 2026-10-20のrunから作った開発例（下のoracleで「由来：E2」と記したもの）と、新しく書いた未使用の例を区別する。開発例だけで一般化を主張しない。

## 2. 結果の区分と集計

| 区分 | 意味 |
| --- | --- |
| `pass` | 前提が成立し、期待の境界を満たした |
| `fail` | 前提が成立し、期待の境界に反した |
| `not_evaluable` | 前提が公開prefix上で成立しない（理由付き）。そのoracleだけに適用し、出典捏造・漏洩・不当な状態昇格の検査は免除しない |
| `precondition_undetermined` | 前提の成否を独立に判定できない |
| `not_reached` | 停止などで該当の段・試行に到達しなかった（どの段で止まったかを記録） |
| `not_measured` | 計測が未実装 |
| `error` | 実行の失敗（一次原因のコードを付け、二次症状をその原因IDへ結ぶ） |

- 総合状態：`fail` が1件以上なら不合格。`error`・`not_reached` があれば「未完了」。評価済み（pass+fail）が0件なら「意味的証拠なし」。それ以外は「評価済みの範囲で合格（n/N）」。
- 予定・試行・到達・評価可能・pass・fail・未評価の件数を、oracle単位と試行単位の両方で分母とともに示す。
- 導入を承認するのに必要な件数・割合は定めない（研究者判断）。

## 3. 前提の判定

- 2b（固定履歴）では前提は台本の公開文で構成上成立する。台本の公開文と前提の対応を事前監査で確認する。
- 2c（自由live）では、前提を被検査の抽出器の出力から判定しない。公開prefixだけを見て、事前に定義した基準でAstraが判定し、システムの局所ラベルを見る前に記録する。前提に未来の発話を使わない。

## 4. oracleの記述形式

各oracleは次を持つ。

| 項目 | 内容 |
| --- | --- |
| id・版・層 | 例：`B1@1`、2b |
| 公開prefix | 該当する公開発話（話者・番号・文） |
| 前提 | どの公開命題が先にあるか。成立しない場合の扱い |
| 作用 | どの先行公開命題に、どの話者のどの分節が、どう作用してよいか（許容集合） |
| 非更新 | 変わってはいけない命題・issue・名称状態・図形候補 |
| 許容される未確定 | `unknown` などを許容するか（許容しても件数を報告する） |
| 失敗の分類 | 期待値／判断／抽出・分類／検証・記憶の粒度／配線 |
| 根拠 | SSOT・決定の該当箇所 |

## 6. 実接続（live）E2Eの予定

- 予算：Luna・Jevの実呼び出しを伴う試行は、台本5〜8本×1回を上限とし、費用（記録値）を報告する。件数は研究上の標本ではなく実装の動作確認である。
- 入力：匿名の合成台本のみ。実参加者データ、相手画像、正解表は使わない。
- 順序：模擬回帰（層1・2a・2b模擬）→ 実Luna/Jevでの2b・2c → Astraの事後監査（前提判定は出力を見る前に記録）。
- 不合格・未到達・評価不能をそのまま報告し、期待やゲートを後から変えない。

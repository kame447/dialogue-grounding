# 局所命題単位の部分更新（opt-in・研究用）

[決定記録 0001](../../decisions/0001-partial-grounding-state.md) の設計原則を実装するための共通契約です。型と閉集合は [contract.ts](contract.ts) にあります。既定の実験条件・方略・採点・UI・モデルポリシーは変更しません。`createDialogueV2` で明示的に有効化した場合だけ動作し、両方略（repair-first / bypass-enabled）で同じ機構を使います。

## 責務

1. **Luna（抽出）**：現在の人間発話を節・部分に分け、引用、自分側の対象候補、論点（`LOCAL_ASPECTS`）、自由記述の命題、既存の局所問題・先行発話へのリンク候補を提案する。
2. **Jev（閉集合の機能判定）**：各部分が、どの先行命題に対する `LOCAL_ACTS` のどれかを文脈付きで選ぶ。判定できなければ `unknown`。生のスコアは研究記録だけに残し、昇格の閾値に使わない。
3. **プログラム（検証）**：引用が公開発話の字句であること、応答先の命題・発話が存在し論点と対象が整合すること、名称が字句として公開発話に出たことを検証し、通ったものだけを参照グラフの `claim` 操作にする。
4. **コミット**：`claim` 操作は同じターンの参照グラフ更新に含め、生成が成功し公開された時点でだけ適用する。失敗・中断・置換されたターンの解釈は反映しない。

## 抽出器の自分側画像入力

`LocalExtractionInput` は、v2判断と同じAI自身の `ownImage: {mimeType, base64}` と `ownAnchors: [{id, bbox: {x,y,w,h}, centroid: {x,y}}]` を必須とする。アンカーは自分の画像のピクセル座標で、ID集合は `ownSlots` と完全に一致する必要がある。抽出器は既存の `ownImageMessage` と同じマルチモーダル形式で画像を受け、公開発話の特徴・見立てを画像と照合して対象を選ぶ。IDや名称だけで推測せず、対象を絞れなければ `targets: []` または複数候補を保つ。抽出結果に新たな根拠フィールドは追加しない。

画像なし・不正形式・アンカー不整合はモデル呼び出し前に `invalid_input` とする。相手専用画像・正解表・gold等は入力メッセージへ投影せず、画像本文はエラー・`lastDiagnostics` に含めない。画像付きの解釈もAI側の仮説であり、画像の送信成功や模擬テストだけで対象同定の有効性を示したとは扱わない。両方略で同じ入力・抽出機構を使う。

## 検証規則（プログラム側の最低限）

- `agree` / `deny` / `name_accept` / `name_reject` / `withdraw` は、検証できた応答先（`respondsTo`）がある場合だけ記録する。応答先が無い・複数あり得る・論点や対象が一致しない場合は棄却し、他の命題は変更しない。
- 「うん」「それでいい」など相槌・指示語だけの部分は、直前の公開AI発話について、コミット済みの主actに由来する primary claim（プログラムが付ける `ai1`）をJevの `respondsToClaimId` が明示している場合だけ、その命題へ結び付ける。名称提案の `ai1` に対する `name_accept` は可能だが、副次的な特徴claim（`ai2` 等）への相槌は曖昧として扱う。primaryが無い・複数ある・応答先が無い場合は `acknowledge` として記録するか棄却し、合意にしない。
- `construe`（「船っぽい」）は見立てであり、名称状態を変えない。名称状態は `aspect: "name"` の `name_propose` と、それに対する相手の `name_accept` / `name_reject` からだけ導く。
- 別の対象（slot）に対する名称提案への受諾は、現在の対象の名称合意に流用しない。
- 対象候補が未特定・複数の部分は、対象を確定させない（`targets: []` または複数候補のまま）。
- 状態（`LOCAL_ISSUE_STATES`、`LOCAL_NAME_STATES`）は記録から毎回導出し、別に保存しない。
- `recordAiClaims` は公開履歴で検証できた名称claimだけを記録する（出典は `ai_hypothesis`）。非公開計画の `discriminatingFeature` からは、公開文との字句一致や言い換えの有無によらず特徴claimを新設しない。既存graphのclaimは削除・移行しない。特徴が消費していた番号は予約し、後続の名称claimのIDとprimary/secondaryの役割を維持する。
- `featureSource` の既定は `none`。現行の共通opt-in経路も `none` に固定し、外部設定・保存判断等から変更できない。`legacy_private_plan` は旧ゲート2か所と明示したlegacy回帰だけの旧記録再現用であり、現行runtimeの機能評価には使わない。旧モードでは従来の `part` claim・引用・IDを再現する。
- 公開AI特徴への人間の同意・否定は、応答先claimが無くなることで棄却される場合があり、特徴への応答のカバレッジが一時的に下がる。これは両方略に同じく適用する暫定停止である。公開文からのAI特徴抽出や意味確認は実装していない。`repairHistory.question`、`previousAction` 等の計画由来情報、既存の旧特徴claimの扱いも未解決である。
- AIの `confirm` と公開された名称候補の組合せは疑問形の `name_propose` とする。`agree` は同じ単一slot・同じ名称字句について、先行する公開済みの人間の `name_propose` がある場合だけ、その直近の提案に対する `name_accept` を記録する。人間の提案が無い・公開出典を確認できない場合は作らない。
- 履歴だけから、公開発話に支持されない同意を新設しない。AIの仮説（`ai_hypothesis`）は正解ではなく、`grounded` も真の指示対象同定を意味しない。

局所問題は `assert` / `construe` 単独では話者によらず `unconfirmed`、検証済みの応答による支持があれば `supported`、否定があれば `denied`、両方あれば `contested` と導出する。名称提案だけなら `unclear`、拒否や受諾後の別名提案なら `not_agreed`、単一対象への対向話者の検証済み受諾がある場合だけ `agreed` とする。撤回した提案の名称は `unknown` とし、以前の名称合意を自動復活させない。これは実装上の保守的な記録規則であり、研究上の正解ラベルではない。

非公開の `summarizeLocalIssues` は状態に加え、各issueの有効な最初の命題・最新の支持・最新の否定・最新更新から重複を除いた最大4件の命題本文と出典を含める。これにより生成器は、どの特徴が支持・否定されたかを区別できる。文字数予算を超える場合はissue全体で省略し、契約型 `LocalIssueView` に本文欄や保存状態は追加しない。

# v2 web: questionnaire, review navigation, earlier trials (2026-10-19)

Participant-side UI for the per-record API in `dialogue-model/runtime/v2/participant-records.ts`
(PR #44): `GET /api/records`, `GET /api/records/:id/review`, `GET/POST /api/records/:id/questionnaire`.
The recordId of the active trial is `state.trial.sessionId`.

## Questionnaire items are provisional

The items come from the server form (`provisional-v0`). They are **trial items for operation checks
(試行用・研究者未承認)**, not an official scale. The UI shows `form.notice` verbatim and adds a fixed
「試行用・研究者未承認」 badge. It never computes a total. Wording, scale and timing are research
decisions that are still open (see `dialogue-model/README.md`).

## Flow

- Before the names are submitted: the editable chat ⇄ names flow (unchanged).
- After submission: a review bar lists 会話 / 名前 / アンケート / 結果. The chat and names are
  **read-only** (no composer, no name edits), and a notice says what can still change: the
  questionnaire, until it is submitted.
- Default order: names (waiting for the AI) → questionnaire (once the trial is completed) → results.
  An explicit choice in the review bar wins while that stage is allowed.
- **Results lock (researcher decision, 2026-10-19).** Matches, AI names and the score are shown only
  after that record's questionnaire is **submitted**; a saved draft never unlocks them. This holds on the
  board, the results stage and the review bar, for new trials and for earlier records alike. The 結果
  tab stays pressable but leads to the questionnaire with 「アンケートの提出後に結果を表示します。」.
  The server withholds `result` and sends `resultLocked: true` until submission. The UI never shows a
  result it did not receive, and refetches `/api/state` or `/review` after submitting. Only an older server
  without the questionnaire API (404/405, no lock) shows a received result directly.
- An unsubmitted questionnaire shows a prompt on every other stage.
- If the API answers 404/405 (an older deployment), the UI goes straight to results and the step
  keeps its 予定 label.

## Drafts and data loss

- Every change is written to `localStorage` at once (`joint-naming-survey:<recordId>`, try/catch).
  The browser copy is kept **only until the server has the draft**, then removed. On load, copies for
  records that `/api/records` no longer lists (expired, deleted or another cookie's) are removed, so no
  answer outlives its record. Changes also go to the server as a draft after 2 s without edits, before leaving the questionnaire, and with
  `keepalive` on `pagehide` or a hidden tab. Failed saves (including 429) retry after 10 s, and the
  status line says the browser copy is kept.
- After a reload, browser edits that never reached the server win over the server draft and are resent.
- Shared devices: operators should clear the site data (Cookie and storage), not only the cookie.
  A submitted questionnaire always wins, and its browser copy is removed.
- No `window.confirm`/`alert`. 「研究者用：次の試行を準備」 needs a second press while a
  questionnaire is unsubmitted, and that trial stays reachable under 以前の試行.

## Earlier trials

A banner 「このブラウザの以前の試行」 (from `/api/records`, cookie-scoped) appears on every screen,
including the start screen and while a newer trial is active. Each completed record has 会話を見る and,
unless submitted, アンケートに回答/再開. Opening a record shows it read-only in the same screens.
Polling of the active trial pauses meanwhile, and 「現在の試行に戻る」 restores it, including its
name memo and any unsent composer text. A record cannot be opened while a message is still being sent.

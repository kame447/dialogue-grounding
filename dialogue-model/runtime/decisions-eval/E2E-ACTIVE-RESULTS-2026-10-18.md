# Active judge の実 E2E 結果（2026-10-18、実験外・診断用・研究者未承認）

計画は [E2E-ACTIVE-JUDGE-PLAN.md](E2E-ACTIVE-JUDGE-PLAN.md)、監査は [ACTIVE-JUDGE-AUDIT.md](ACTIVE-JUDGE-AUDIT.md) と [HOLISTIC-AUDIT.md](HOLISTIC-AUDIT.md)。プロトタイプの動作確認であり、実験結果・方略効果・モデルの優劣の証拠ではありません。判断モデルは既定で無効です。

## 条件

- 刺激: 研究で生成した合成タングラム6図形。seed 137（人間役にとって未見）、repair-first、参照メモリ ON。AI はAI側盤面だけ、人間役（Opus）はブラウザの人間側盤面だけを見た。
- 経路: ローカル研究サーバ（`--active-decision-judge`）→ 研究用 Worker → OpenAI（Luna の解釈・発話）／OpenRouter（判断モデル）。鍵は Worker の Secret だけ。送ったのは合成図形と合成対話だけ。
- 人間役は、AI盤面・正解表・非公開の作業メモ・評価結果を、各セッションの双方提出まで見なかった。発話は短く1手ずつで、答えを先に渡していない。
- セッション1: Jev 1.14 active。セッション2: GPT-6 Luna Decisions active。同じ seed・役割・方略で、人間役はできるだけ同じ順序・同じ最初の言い方で進めた。

## 結果

| 指標 | セッション1（Jev） | セッション2（Luna Decisions） |
| --- | --- | --- |
| 人間の発話数／AIの応答数 | 15／15 | 14／14 |
| 一致数（双方の名称対応） | **2/6** | **1/6** |
| 判断モデルの選択 | confirm 12・accept 2・agree 1 | confirm 11・accept 2・agree 1 |
| Luna 自身の解釈の action | confirm 6・agree 3・propose_name 3・accept 3 | propose_name 7・confirm 3・accept 3・agree 1 |
| 最終 action | accept 7・confirm 6・agree 2 | accept 8・confirm 2・propose_name 2・move_on 2 |
| 解決の内訳 | 判断モデルどおり 8・再順位 7 | 判断モデルどおり 4・再順位 10 |
| 判断モデルが Luna と異なる回 | 8 | 11 |
| 台帳上の合意（うち誤り） | 2（2） | 0 |
| 修復 | 0 | 0 |
| agree 以外なのに「呼びましょう」等と発話 | 4 回 | 6 回 |
| 判断モデルの遅延（中央値／p90） | 390／566 ms | 532／698 ms |
| 判断モデルの費用 | $0.00089 | $0.00130 |
| Luna 呼び出し（判断＋発話） | 34 回、中央値 8.9 s、エラー 0 | 31 回、中央値 6.8 s、エラー 0 |

- 取り違え: 両セッションとも、同じ図形群（人間側の 家・稲妻・猫・滑り台）が AI 側で循環的に入れ替わった。セッション2では 鳥の頭 と 滑り台 も入れ替わった。一致したのは 鳥の頭・帽子（S1）、帽子（S2）。
- 確認の過多: 判断モデルは両方とも、実対話では約8割で confirm を選んだ（合成評価では Jev は明示的な採用に 9/10 で agree した）。Luna の解釈に特徴があると confirm が有効になり、「〜の形のことですか？」の分析的な質問になった（S1 の 稲妻 は3回連続）。特徴がないと confirm は検証で無効になり、再順位で accept・propose_name・move_on になった。
- holistic-first の効果: 初回の見立てへの応答は、多くの回で短い全体の見立てだった（例: 家・鳥の頭・帽子・Z の初回）。Luna 自身の confirm は S1 6回 → S2 3回。ただし、名前を確定しようとする回では、Luna・判断モデルとも確認に寄った。
- 確認でも取り違えは防げなかった: 家・稲妻の確認で AI が示した特徴は、人間役の図形にも当てはまるものだった。人間役はそれを認め、誤った対応のまま進んだ。

## 見つかった不具合と対応

1. **agree 以外の action で合意を発話**（S1 4回・S2 6回）: active judge が Luna の agree や名前提案を accept 等に変えても、相手が名前を提案していると、生成器が「呼びましょう」と発話した。台帳と公開発話が食い違う。生成依頼に action の表現範囲を明示する修正を入れた（`41b5259`、GrayLavoisier 実装・BriskPasteur 監査）。記録した2回を実 Luna で再生（各2回）すると、合意表現は 4回中2回に減ったが、残った。**未解決**: 指示だけでは不十分。
2. **agree の保守的ゲート**により、判断モデルは合意を始められない（設計どおり）。S2 では台帳上の合意が0のまま、公開発話では毎回合意していた（上の不具合）。
3. 別ポートの模擬サーバと同じブラウザで試すと、Cookie がポートで分かれないため研究サーバのセッションが失われた（運用上の注意）。

## 限界

- 2セッションだけで、seed も1つ。勝者は決めない。
- 人間役（Opus）は seed 137 の自分の盤面をセッション1で学んでおり、セッション2では同じ名前・同じ順序を使った（学習の偏り）。人間役自身の見立ての誤り（AIの説明への安易な同意）も結果に含まれる。
- 判断モデルは Luna の解釈（対象・名前・特徴の仮説）を文章で受け取り、画像を見ない。Luna から独立した判断モデルの比較ではない。
- 実人間・実参加者での妥当性は未検証。

## 研究者の判断が必要な点

- 判断モデルの confirm への偏り（入力が画像なしの文章で、Luna の仮説に「正解ではない」と明記されていること）が原因かどうかを、入力を変えて調べるか。
- 合意の保守的ゲートを続けるか。続けるなら、相手の明示的な命名への自然な応答と、台帳上の合意をどう整合させるか。
- 取り違えの主因は、向きで変わる見立てを言葉で対応付けることにある。確認の回数ではなく、確認の中身（両方の図形を区別できる特徴）をどう引き出すか。

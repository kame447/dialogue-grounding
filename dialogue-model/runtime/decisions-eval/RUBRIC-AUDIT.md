# Decisions 評価ルーブリックの独立監査

**エンジニアリング用・研究者未承認。** これは評価基準への批判と実装検査であり、研究上の採用、妥当性の証明、モデルの優劣、方略効果の実験結果ではない。正本は [../../README.md](../../README.md)。2026-10-18、PLAN の起点 `064bfed` と Worker の9行動、v2 教示・判断検証を対象とする。

## 第1段階：ケース作成前の指摘

### 1. 「危険」「不許容」「未評価」を区別する必要がある（重要度 P1）

`acceptable` は、その時点の公開履歴とAI自身の利用可能情報から、次の一手として課題を合理的に進められる行動の集合と解釈する。単なる「直ちに害がない」ではない。`dangerous` は、誤った名称確定・根拠のない自己訂正など、具体的に説明できる失敗を起こす行動に限定する。どちらにもない行動は「正しい」ではなく中立／未評価である。集合が交わらないことは機械検証できるが、内容の妥当性は保証しない。

たとえば `accept` は合意を作らないため安全でも、明示的な訂正要求に毎回相槌だけで返すなら問題を解かない。安全性だけを最適化すると、常に `accept` する停止方略が高得点になりうる。一方、`confirm` が進行を遅らせるだけの場面と、既に確定した名称を再び不確かに扱う場面は害の程度が違う。「確認が不要」という研究者の好みだけで一律に危険へ分類しない。

提案：各ケースの根拠に、(a) 現在の参照対象の識別根拠、(b) 名称を共同採用する意思の根拠、(c) 未解決問題、(d) 過去の公開上の責任・合意、(e) 次の一手が満たすべき機能、を分けて記録する。これらは**ローカル注釈**であり、その解答を言うために model state に追加してはいけない。根拠が状態から判断できなければ、ラベルを広げるかケースを除外する。

### 2. 三つのリスク率は機会母数が違い、足してはいけない（P1）

「誤agree」は客観的な図形対応の誤りではなく、ここでは**暫定ルーブリックが危険とした agree の選択**である。合成テキストのみでは、本当に相手と同じ図形を指したかを検証していない。「過剰confirm」「不当repair」も同様にラベル依存の測定である。

各率の母数は、その行動が `dangerous` に含まれるケース数を明示する。欠測を母数から除くのか、全予定ケースで数えるのかも区別し、少なくとも予定数・有効回答数・危険選択数・無回答数を併記する。母数0は0%ではなく null／適用外とする。無回答だらけのモデルを安全と解釈しない。

単一 choice の一回答は agree と confirm と repair を同時に選べない。しかし同じケースは複数のリスクの「機会」に含まれ、危険率にも同じ誤りが含まれる。分母の異なる三率を加算したり、危険率と誤agree率を足した総合点を作ると二重計上になる。許容・危険・中立・無回答を別々に数え、三率は重み付き総合点にせず診断として表示する。

危険ケースにおける P(agree) の平均・最大は判断確率の記述であり、図形同定の確信度や校正精度ではない。許容行動が複数ある場合に、承認なしに単一の確率正解・最適閾値を作らない。モデル一致率も正しさを保証しない。

### 3. v2 の実行可能性と研究上の妥当性は別（P1）

現行 v2 は `unassigned`／`deferred` の対象への agree を、特徴があっても `agree_requires_shared_identification` で拒否する。Worker の `ACTION_CRITERIA.agree` は「同じ対象を識別でき、相手にも共同採用意思がある」と説明し、ledger 状態や一往復待つ制約までは表現していない。評価 state は Worker の問題文と短い履歴・AIの未検証仮説だけを渡し、v2 の全教示は送らない。

したがって、このガードへの一致を「判断の正解」と呼ばない。合成の公開情報から十分に識別・共同採用できても ledger が未割当なら、自然な行動としての agree と、今のプログラムが許す agree は一致しないことがある。逆に tentative は対象の同定を保証せず、仮名を持っているだけで agree が正当になるわけではない。基準を「対話上の許容行動」とするか「現行ランタイムに実装可能な行動」とするかを先に宣言し、後者の制約は別の適合性検査にする。

v2 教示にも、相槌への agree は直前の識別特徴がある場合だけという説明と、以前に特徴を示していなければ agree に新たな特徴を添えるという説明が同居する。この不整合を一方のラベルだけで密かに解消しない。相槌については、前の提案の内容・当該対象への結び付き・共同採用意思を含む対例を用意し、争点として研究者に示す。

### 4. 層ごとに判断が割れる点（P2）

| 層 | 単純なラベル付けが危険な理由 | 必要な対例・注意 |
|---|---|---|
| impression_only / unidentified_referent | 見立てを共有するだけの開始に、必ず確認が必要とは限らない | accept と全体の見立て提案を許すか、識別・名称確定が迫る局面と分ける |
| multiple_similar_candidates | 候補数だけで必ず質問するとは限らない | 今すぐ割当が必要なら confirm、保留・進行が有用なら defer / move_on も検討 |
| explicit_adoption | 名前採用の意思と参照対象の識別は別 | 明示的な名前があっても対象未同定の対例、識別済みの対例を分ける |
| bare_backchannel | 「はい」は提案の受入れにも単なる聴取にもなる | 直前のAI発話が命名提案・識別確認・一般説明のどれかを明示する |
| explicit_repair_request | 聞き返しと、AIの過去の誤対応を訂正する要求は異なる | 「意味が分からない」だけで repair 必須にしない。既存の誤った公開主張／割当を確認 |
| defer_request / later_reprocessing | 保留は課題放棄ではなく、再訪は未解決の確認と両立する | 再訪時の revisit と confirm、保留要請への defer と受け止めの許容幅を検討 |
| progress_priority | 課題進行への要請が、未確認の対象を合意扱いする許可にはならない | move_on / defer と agree を分ける。修復すべき実害がある場合は無視しない |
| suboptimal_agreement | 詳細な見立ての違いと対象の取り違えを混同しやすい | 同じ図形を共同で識別できれば、見立ての完全一致を成功条件にしない |
| closing | 終了相談と6図形の完成宣言は別 | close は終了を相談する行動。未完了だから常に危険とはしない |
| self_correction_needed | AI内部の未公表仮説の更新は、公開した誤りの撤回とは限らない | 公開責任のない仮説なら confirm / accept / 仮名更新も検討。過去の誤った合意があれば repair |

各層の3〜5例を独立な観測のように扱って信頼区間や一般化を論じない。同一テンプレートの名前置換は、独立した推論難易度の追加ではない。

### 5. 方略ペアは情報条件を同一にし、価値判断を別表示する（P1）

方略間で変えてよいのは、方略の指定と方略ごとの許容・危険ラベルだけ。発話順・人物・AI候補・ledger・仮説・名前・特徴が異なるペアでは、方略効果を識別できない。生成 state では `strategy` だけを除去して、残る JSON の完全一致を検査する。両モデルにも同じ state と同じ Worker questions を送る。

合理的な差は、不確かさへの**応じ方とタイミング**である。repair-first の confirm と bypass-enabled の defer / move_on などは異なってよい。一方、明示的な訂正要求を無視する、対象未同定で合意する、過去の誤合意を黙って付け替える、といった行為を片方だけ正当化しない。bypass-enabled は確認禁止ではなく、repair-first も必要な保留を禁止する条件ではない。方略に一意の行動を強制する評価は、正本の比較を作り替える。

ラベル差は全件を一覧化し、ケースごとに情報の相違ではなく「許容される応答方針」の差で説明できるかを人が確認する。戦略ペアや2モデル分の行を、別々のベースケース数に数えない。

### 6. 漏洩はキー名検査だけでは防げない（P1）

`acceptable` / `dangerous` / `rationale` / `stratum` / case ID / 正解表などのメタデータが state にないことを、保存行ではなく**実際に送るシリアライズ済み state**で検査する。ラベルだけを変えても state が変化しないことを確認し、Worker の固定 questions にケースごとの採点メモを混ぜない。

ただし、状態本文に「この場面では agree が危険」「対象はすでに同定済みだから合意すべき」などと答えを書くと、キー名がなくても意味上の漏洩になる。後者の判断を正当化する観察・公開発話を示すべきで、評価者の結論をAIの既知の事実として与えない。架空の ledger／AI仮説は許されるが、相手の内面・正しい図形IDの対応・未来の反応を含めない。

図形画像がなく、AIの視覚仮説をテキストで与える現評価は「与えた仮説を前提とした行動選択」の検査であり、回転した画像の認識・図形弁別・実際の共同命名成功の評価ではない。漏洩検査の合格だけで外的妥当性を主張しない。

### 7. 9択問題と退化方略（P2）

9行動は自然な発話の排他的な分類ではない。accept は他行為の前置きにもなる。repair と confirm、defer と move_on、revisit と confirm は1発話で共存しうる。v2 の主判断＋ followUp と、Worker の単一 choice は表現力が異なる。単一 choice の便宜上、主な機能を選んだのか、次の一手のいずれかを許すのかを揃える必要がある。

語彙・行動定義・並び順と候補数も選択確率を左右しうるため、P(agree) はこの固定9択での確率として扱う。異なる設問や行動集合の数値と無条件に比較しない。対話履歴に `保留`／`戻る` などの語があるだけで正解できるテンプレートへの依存も確認する。

最低限、9つの定数方略（常に同じ行動）、無回答方略、全行動一様確率の基準を**同じ scorer**で出す。層別・方略別にも許容率／危険率／中立率を示す。常に accept / confirm / defer がモデル並みなら、モデルが理解した証拠にならない。全件の許容集合に共通する行動があれば、その退化解を明示する。層の出現比率を反映する micro 集計だけでなく、層ごとの重みを均等にした macro 集計を併記すると、テンプレートの本数の偏りを発見しやすい。

## 第1段階へのエンジニアリング上の応答

親 WildBose は ORRERY #6162 で PLAN に追記した。基準を対話上の許容性に固定し、v2 ガードとの相違は `runtimeGuardBlocks` として別表示、四分類・母数0の null・定数／無回答／一様基準・層別 macro・構造化 rationale・送信 state の方略ペア同一性検査を採用する方針である。これは実装計画の明確化であり、研究者による尺度・ラベル承認ではない。

GrayLavoisier の設計では、選択率の母数に予定対象の無回答も含め、回答率を別に表示する。これは可能な定義だが、無回答を減らしたかと判断を改善したかを混同しない。一致率は両モデルが有効回答したペアを母数にし、予定ペア数も併記する。

- 追加の解釈上の争点として残したのは **6ベース／12ケース**：019、020、036–038、043。危険なコード欠陥の認定ではなく、研究者によるルーブリック確認事項である。039 の方略差もこの争点を共有するが、上記9件側に一度だけ数えた。

### 具体的なラベル勧告と残る争点

**P2・変更済み：001–005。** 初期版は全件 confirm を許容していたが、公開文に識別の迷い・複数候補・詳細要求などの確認トリガーがない。特に004の「そちらは？」や005の見立ての違いは、直ちに図形の取り違えを意味しない。confirm を危険にせず中立へ移すことを提案し、両方略で改定された。

**P2・変更済み：025、026。** 025は名称を承認していないという明示的否定で、形状を質問し直す問題ではない。026も「舟」と「冠」の呼び違いが明示され、追加の対象不明性は示されていない。初期の confirm 許容は、必要な自己訂正を幾何学的確認で代替してよいと採点していた。両件とも repair のみ許容、confirm は中立へ改定。026の `rationale.openIssue` に判断理由を残している。

**P2・変更済み：013。** 相手は「魚の候補は一つだけか」を尋ね、AI仮説には二つあると記されている。正直に数を答える機能が9択にないため、confirm / defer だけでは応答を不当に落とす。accept を追加し、inform がないという分類上の限界を rationale に記録した。これは accept の実際の発話内容まで保証しない。

**P2・変更済み：039。** 相手は現在の難しい区別を置き、説明しやすい次の対象を明示的に求めている。defer / move_on / confirm だけでは、次の名前を提案する自然な応答を許容しない。両方略に propose_name を追加した。ただし、同じ対象へ再提案してしまう誤りは action だけでは識別できない。

**P2・研究者確認：019、043。** 相手が同じ確認の反復を明示的に拒んでおり、反復 confirm を負担・不適切性のストレスケースにする根拠はある。しかし、choice の confirm には「同じ確認を繰り返す」か「新しい重要な食い違いを解く」かが含まれていない。ここでの危険は限定した会話上の拒否への不応答であり、あらゆる追加確認が危険という一般則ではない。現ラベルを自動で広く一般化しない。

**P2・研究者確認：020。** 識別特徴付きの命名提案に「はい」と答えるため、agree を一律の誤りにしない設計は適切。一方、聴取・対象認定・名前採用の解釈は研究者間で割れうる。confirm も許容しているのはこの争点への対応であり、肯定語だけから正解が決まることを示さない。021（特徴なしの提案）、022（一般的な感想）、023（特徴質問への非回答）との対比を維持する。

**P2・研究者確認：036–038、および039の方略差。** repair-first では confirm 許容、bypass-enabled では中立となる。情報と危険集合は同じで、明示的な進行要請に対し追加確認をどれだけ優先するかという価値判断だけが異なる。曖昧さ許容条件は確認禁止ではないので、中立は「禁じる」ではなく「このルーブリックでは積極的許容の得点を与えない」と説明する必要がある。研究者がこの差を妥当としなければ、共通ラベルによる感度分析も検討する。

**P2・scorerの入力検証：修正済み。** 初期 `validate` は同一集合内のラベル重複を拒まず、たとえば acceptable=[accept,accept] の1ケースを常にacceptで採点すると許容数2・率200%となった。実際の固定ケースに重複はなかったが、改定時の事故を防げない。duplicate acceptable / dangerous を拒否する修正と独立回帰テストを確認した。

### 定数方略・一様基準：改定後の実測値

同じ `scoreResults` / `scoreBaselines` で100方略ケースをローカル採点した。モデルの推論結果ではない。許容／危険／中立の件数は各行で100となる。

| 常に選ぶ行動 | 許容 | 危険 | 中立 | 許容率 micro | 層を均等重みとした許容率 macro |
|---|---:|---:|---:|---:|---:|
| accept | 30 | 0 | 70 | 30% | 30.56% |
| propose_name | 18 | 0 | 82 | 18% | 16.67% |
| confirm | 50 | 4 | 46 | 50% | 50.69% |
| repair | 10 | 80 | 10 | 10% | 10.42% |
| defer | 34 | 0 | 66 | 34% | 33.33% |

| agree | 20 | 76 | 4 | 20% | 18.75% |

初期版で常に confirm の許容率は64%（repair-first 68%、bypass-enabled 60%）だった。改定後は50%（54%、46%）。**この方略間8ポイントの差は、行動が全く同じでもラベルだけで生じる。モデルの行動差・方略効果ではない。** 最も許容される定数方略であっても、人間に適した方略であるとは結論できない。

常に accept / defer / close などは危険率0でも、大半が中立のまま止まる。安全性の低リスク値だけを最適化してはいけない。全ケースで許容される一つの行動はなく、常に confirm でも半分は許容に入らない。モデルはこの基準と層別の機能を超えているかを検討する必要がある。

無回答基準は100件無回答・許容0・危険0・中立0で、回答率0。これは安全性の達成ではない。一様確率基準はサンプリングではなく、同一 scorer の確率重みによる期待件数で、許容20.8889、危険17.7778、中立61.3333、無回答0。各危険行動の対象内選択率は1/9で、合計値ではない。

# 候補衝突と弁別的確認（opt-in 介入）の検証（2026-10-19、実験外・研究者未承認）

候補衝突（candidate conflict）の opt-in 介入を、実装したうえで小規模に検証した記録です。採用・不採用の提案ではありません。研究条件、方略、刺激、採点、尺度は変えていません。既定は無効で、既定の v1/v2 判断プロンプト（再提出要求を含む）は 6377de9 とバイト単位で同一です（テストで固定）。

## 何を足したか

- `createLunaJudge(client, { candidateConflict: true })`（v2 だけ）。判断 JSON に非公開の `conflict` を追加で求める。
  - `candidates`: 現在の対象の見立てに当てはまりうる自分の図形が2つ以上あるときだけ、自分の内部ID 2〜3個と、それぞれを他の候補から区別する特徴1つ。1つ以下なら空配列。
  - `featureFits`: `discriminatingFeature` を使うとき、その特徴が自分の画像で当てはまる候補ID。
- 決定的な規則は1つだけ: 候補が2つ以上あるのに、`featureFits` が空、または全候補になる特徴は `non_discriminating_feature`。一度だけ訂正を求めて再提出させる。再提出後も同じなら、検証済みの行為はそのまま残し、`nonDiscriminating: true` を非公開で記録する。
- 監査 B1 に合わせ、`conflict` の欠落・形式不正・対象が候補外などの問題では、有効な行為を捨てない。`conflict: null` と `conflictError` を記録するだけで、`SAFE_JUDGMENT` に落とさない。
- 指示文は両方略で同一。方略差は `JUDGE_POLICIES` だけ（テストで確認）。「候補が複数あること自体は確認のトリガーではない」と明記し、確認・保留・移行の選択は既存の分析トリガーと方略に任せる。
- `conflict` は判断器の診断（研究記録の `validation`）にだけ残る。生成器には渡さない（テストで確認）。モデルが見るのは、自分の画像、自分のアンカー、公開発話だけ。
- 正解鍵を使う採点器は `diagnostics/candidate-conflict-score.ts` に置いた。ランタイムはこれを import しない（テストで確認）。真の指示対象は AI の選択からは作らず、非公開の gold 注釈を鍵で AI 側 ID に写したものだけを受け付ける。

## 方法

- 刺激: 合成タングラム seed 137（記録済み E2E と同じ盤面）。判断は実 Luna（研究用 Worker 経由、`purpose=dialogue_turn`、gpt-6-luna）。
- **E2E 接頭辞の再生**: 2026-10-18 の active judge E2E 記録 2本（S1: 15ターン、S2: 14ターン）について、各人間ターンまでの公開発話と、その時点の AI の作業メモで判断だけを再実行した。S1+S2 は repair-first で既定と opt-in を比較し、S1 は bypass-enabled でも比較した。各条件で1回だけ標本を取った。参照メモリはその時点のグラフが記録にないため OFF にした（記録時は ON）。
- **合成ケース**: `decisions-eval/cases.mjs` の8ベース（006, 011–014, 015, 020, 036）× 2方略 × 既定/opt-in。画像は seed 137 の AI 盤面で、ケースの ID をアンカーに順に割り当てた。合成ケースには対話上の gold 指示対象がない。そのため指示対象の正誤は評価せず、ケースのラベル（許容／危険な行為）だけで見た。
- **特徴の当てはまり採点**: 判断に出た特徴と候補特徴の計67個を、別の Luna 呼び出しで採点した。採点器には自分の6図形の切り出し画像（A〜F、ID と無関係な順序）を見せ、各特徴が当てはまる図形を選ばせた。切り出しと ID の対応は採点スクリプトだけが持つ。採点器は判断と同じモデルなので、独立した評定ではない。
- **gold 指示対象**: 親エージェント WildBose による human-role 注釈（独立した注釈者ではない）。WildBose は両セッションで人間役を務めた。各ターンの話題語の図形を指示対象とし、答えるだけのターンは現在の図形とした。注釈ファイルは非公開でリポジトリ外にあり、ここには方法だけを書く。
- **小さな実対話比較**: S1 の人間側の最初の7発話を台本として同じ順に入力し、既定と opt-in で AI の判断と発話を実際に生成した。repair-first、判断モデルなし。人間側は AI の応答に反応しない。
- Decisions（Jev／Luna Decisions）: 研究用 Worker の現行デプロイには `/v1/decisions` がない（404）。試みた60回はすべて失敗し、費用は0だった。再デプロイは権限外のため行っていない。Jev を同じ入力で後から再生できるよう、合成刺激の判断状態92件を非公開で保存した（**Decisions の再開待ち**）。

- 方略差（S1 の同じ15接頭辞）: repair-first 既定は confirm 4・agree 5・propose_name 5・accept 1。bypass-enabled 既定は confirm 0・agree 5・propose_name 6・accept 4。差は confirm と accept・propose_name の間に出た。defer・revisit・move_on は、どの条件でも Luna 自身は選ばなかった。opt-in を有効にしても、この分布はほとんど変わらなかった（repair 3 vs bypass 2 の confirm）。
- 決定的規則（全候補に当てはまる特徴の差し戻し）は一度も発動しなかった。Luna は毎回、候補の真部分集合を `featureFits` として申告した。しかし採点器によれば、申告と実際の当てはまりは 5/8 しか一致しない。この規則が検査できるのは自己申告の整合性だけで、特徴が実際に候補を分けるかどうかは検査できない。
- 主な失敗は候補集合の生成にある。opt-in で候補を挙げた11回のうち、gold の図形を候補に含んだのは2回だけだった。候補同士を分ける特徴を正しく選べても、誤った候補どうしを分けるだけでは取り違えを防げない。
- タングラム特有の点: 6図形はどれも同じ7片（大三角2・中三角・小三角2・正方形・平行四辺形）でできている。そのため「四角い突起」「大きな三角」のような部品の特徴は、ほぼ全図形に当てはまる（採点器ではそうした特徴の多くが6/6、または5/6）。弁別に使えるのはシルエットの配置の特徴（深いV字の切れ込み、長い斜めの辺など）だけだった。

## 限界

- 条件ごとに1標本で、盤面も seed 137 だけ。E2E の接頭辞は、記録時の AI の誤った作業メモと公開発話を引き継いでいる（agree の誤りはほぼこの継承による）。参照メモリは OFF で、記録時とは異なる。
- 特徴の採点器は判断と同じ Luna で、独立していない。人手での確認はしていない。gold は人間役を務めた親エージェントの注釈で、独立した注釈者ではない。
- 判断モデル（Decisions）の active 判断は、Worker にルートがないため評価できなかった。E2E で問題になった「約8割 confirm」が opt-in で変わるかどうかは未検証。
- 実対話比較の人間側は台本で、AI の応答に反応しない。
- 効果の主張はしない。上の数値は opt-in 介入の挙動の記述であり、方略効果・実験結果・画像認識精度の証拠ではない。

## 使用量

- Luna: 合計173回（判断の再生 93、合成 36、採点 15（うち8回は Worker の1メッセージ4パート上限で 400 になり、採点結果は得ていない）、実対話比較 29）。上限は200回。トークンは再生と合成で入力約735k・出力約135k。採点と実対話比較のトークンは集計していない。
- Decisions: 試行60回＋疎通確認2回。すべて 404 で、費用は0。

## 研究者の判断が必要な点

- 候補集合に正しい図形がほとんど入らない。改善するなら、確認の中身より前に、候補の生成（回転を越えた全体の対応付け）を扱う必要がある。それを介入として検討するかどうか。
- 自己申告の `featureFits` は真偽を検査できない。採点器なしで弁別性を保証する方法（例: 候補の切り出しを個別に見せて自己照合させる）を検討するかどうか。その場合は入力が変わるので、研究条件として扱う必要がある。
- bypass-enabled では、保留・移行（defer／move_on／revisit）が Luna 自身からは出なかった。方略差が confirm の有無だけに現れることを許容するか。
- Decisions の再開後に、保存した入力で Jev の active 判断を再生するかどうか（入力は同一、判断モデルだけを変える）。
